# SPARK LIST 設計文件

日期：2026-07-29
狀態：已通過使用者確認，待寫入實作計畫

## 1. 產品概述

SPARK LIST 是一款「衝動購物冷靜期」App。使用者把讓自己「被生火」（心動想買）的單品丟進 App，設定一個解鎖日期，經過冷靜期後仍然心動、且符合理性消費的判斷條件，才允許購買；否則就必須刪除放棄。

核心設計理念：把「理性消費檢查」轉化成一個有音效回饋、有段位晉升感的遊戲化體驗，讓「忍住不買」變成值得慶祝的事，而不是單純的自我剝奪。

## 2. 核心機制

1. 使用者看到心動單品，加入 App，設定**解鎖日期**，並勾選符合的**六項條件**（初次可能勾不到 3 項，之後可隨時回來補勾或取消勾選）
2. 等待期間單品停留在「冷靜區」，使用者可隨時修改條件勾選狀態、修改解鎖日期，或主動放棄刪除
3. 當「解鎖日期已過」**且**「六項條件勾選數 ≥ 3」**同時成立**時，自動觸發解鎖：播放歡呼音效、跳出本機通知、單品移入「解鎖區」
4. 「單品仍留在清單中未被刪除」本身即代表使用者依然心動；不需要另外詢問「還想買嗎？」
5. 只要是「沒有真的購買、主動刪除單品」的行為（無論發生在冷靜區或解鎖區），都會播放煙火音效並獲得 1 點「忍術點數」，累積可晉升忍術段位

### 解鎖判斷邏輯

- 觸發時機：每當單品的 `unlockDate` 或 `conditionChecks` 有變動時，重新檢查一次
- 判斷式：`(now >= unlockDate) AND (勾選數 >= 3)` 同時成立 → 狀態由 `cooling` 轉為 `unlocked`
- 若日期已過但勾選數未滿 3：單品**繼續留在冷靜區**，不強制刪除，等使用者自己繼續勾選或主動刪除
- 若日期未到但勾選數已滿 3：單品仍留在冷靜區，等日期到才解鎖（兩條件缺一不可）

## 3. 頁面架構（三分頁）

### 第一頁：我的
- 忍術勳章/段位展示（目前累積點數、現有段位、離下一段位還差幾點）
- 統計數據（累計主動放棄次數、估計省下的金額總和）
- 六項條件自訂入口（編輯預設的六項文字）
- 主題色設定
- 其他設定（本機通知開關等）

### 第二頁：冷靜區
- 「新增單品」入口：填寫名稱、照片、價格、購買連結（可選）、備註（可選），設定解鎖日期（可手動選日曆日期，或用預設天數快捷按鈕如 7/14/30 天），並勾選六項條件的初始狀態
- 尚未解鎖的單品清單，**按解鎖日期排序，最接近解鎖的排最上面**
- 單品操作：隨時修改六項條件勾選狀態、隨時修改解鎖日期、主動刪除（+1 忍術點數 + 煙火音效）
- 距解鎖日剩 3 天時，跳出本機通知提醒「再堅持一下，就快解鎖囉！」

### 第三頁：解鎖區
- 已同時符合「日期已過」+「條件≥3 項」的單品清單
- 單品操作：
  - 標記已購買（移出清單並寫入歷史記錄，狀態 `purchased`，**不算**忍術點數）
  - 直接刪除（移出清單並寫入歷史記錄，狀態 `resisted`，**仍算** 1 點忍術點數 + 煙火音效，因為忍住沒買）
  - 點擊購買連結，跳轉外部瀏覽器/購物網頁

## 4. 資料模型

### 單品（Item）

| 欄位 | 型別 | 說明 |
|------|------|------|
| id | string | 唯一識別碼 |
| name | string | 名稱 |
| photoUri | string | 照片本機路徑 |
| price | number | 價格 |
| url | string（optional） | 購買連結 |
| note | string（optional） | 自由備註 |
| createdAt | string（ISO date） | 建立時間 |
| unlockDate | string（ISO date） | 解鎖日期（可事後修改） |
| conditionChecks | boolean[6] | 六項條件勾選狀態，依索引對應目前的六項條件文字 |
| status | `'cooling' \| 'unlocked'` | 目前只有這兩種 active 狀態；`purchased`／`resisted` 屬於歷史記錄專用狀態，一旦轉換即從 active 清單移除 |

### 歷史記錄（HistoryLogEntry）

單品被標記已購買或主動刪除時，寫入一筆歷史記錄（不保留完整單品物件，只留統計所需摘要），供「我的」頁面的統計數據使用：

| 欄位 | 型別 | 說明 |
|------|------|------|
| id | string | 唯一識別碼 |
| itemName | string | 單品名稱（快照） |
| price | number | 價格（快照） |
| outcome | `'purchased' \| 'resisted'` | 結果 |
| recordedAt | string（ISO date） | 發生時間 |

### 全域狀態（Zustand store）

| 欄位 | 說明 |
|------|------|
| ninjaPoints | 目前累積忍術點數 |
| currentRank | 依點數門檻（3/10/20/50/100）計算出的段位 |
| conditionLabels | 六項條件文字（預設值，使用者可編輯覆蓋） |
| themeColor | 主題色偏好 |

## 5. 六項條件（預設值，可於「我的」頁面自訂編輯）

1. 可做出三套穿搭嗎？
2. 我可以在一個月內完全不用思考就穿出門嗎？
3. 符合我的風格嗎？
4. 我已經有類似的單品嗎？
5. C/P 值夠高嗎？（值得嗎？）
6. 材質/洗滌方式我夠了解嗎？（耐用度高嗎）

條件的勾選判斷交由使用者自行認定「這項對我來說是支持購買的」，App 不做語意判斷，純粹是輔助自我反思的檢查清單。條件文字可編輯，但編輯只影響往後顯示的文字，不會回溯修改既有單品已記錄的勾選狀態（勾選狀態只依索引位置對應）。

## 6. 遊戲化機制

### 忍術點數與段位

- 觸發時機：任何「主動刪除且未標記已購買」的行為（不論冷靜區或解鎖區）都 +1 忍術點數，同時播放煙火音效
- 段位門檻：3 點＝忍術小達人｜10 點＝王牌忍術師｜20 點＝金牌忍術師｜50 點＝白金忍術師｜100 點＝鑽石忍術師
- 點數跨過門檻的當下（升級瞬間），額外顯示一次「升段慶祝」提示，與平常的煙火音效做區隔

### 通知與音效時機

| 時機 | 觸發內容 |
|------|---------|
| 距解鎖日剩 3 天 | 本機推播通知：「再堅持一下，就快解鎖囉！」 |
| 日期已過 + 條件≥3 同時成立（解鎖瞬間） | 本機推播通知；使用者點開通知或該單品時播放歡呼音效 |
| 主動刪除單品（未標記購買） | 立即播放煙火音效 + 忍術點數 +1（跨門檻時另加升段提示） |

### 通知的排程與取消

- 新增單品或修改解鎖日期時，重新排程「剩 3 天」與「解鎖日」兩則本機通知
- 單品被刪除或標記已購買時，取消尚未觸發的排程通知，避免對已不存在的單品發出提醒
- 若使用者未授權通知權限，僅影響提醒功能，App 內「冷靜區」清單本身仍會依日期排序正常顯示，不影響核心功能運作

## 7. 技術架構

沿用 `REUSABLE_INFRA.md` 骨架：

```
React Native 0.81.x + Expo SDK 54
Expo Router v6（file-based routing，三分頁採 tab navigation）
TypeScript（strict）
Zustand v5（忍術點數/段位、主題色等全域狀態）
Jest + jest-expo + @testing-library/react-native
EAS Build
```

新增模組（SPARKLIST 專屬）：

| 模組 | 用途 |
|------|------|
| `@react-native-async-storage/async-storage` | 單品清單、歷史記錄、全域狀態持久化 |
| `expo-image-picker` | 新增單品時拍照/選照片 |
| `expo-notifications` | 排程「剩 3 天」「解鎖日」本機通知 |
| `expo-audio` | 播放煙火音效、歡呼音效 |

資料儲存採 **方案 A：AsyncStorage + JSON**（非 SQLite）。理由：App 資料量小（個人購物清單，頂多幾百筆），不需要關聯式查詢能力，AsyncStorage 實作與測試成本最低，符合 YAGNI 原則。

### 資料流分層

```
AsyncStorage
  └─ services/itemService.ts       純函式：CRUD 單品、判斷解鎖條件、寫入歷史記錄
  └─ services/badgeService.ts      純函式：忍術點數計算、段位判斷
       └─ hooks/useItems.ts        封裝清單狀態 + reload()
       └─ hooks/useBadges.ts       封裝點數/段位狀態
       └─ hooks/useNotifications.ts   封裝本機通知排程/取消
            └─ app/(tabs)/me.tsx        「我的」畫面
            └─ app/(tabs)/cooling.tsx   「冷靜區」畫面
            └─ app/(tabs)/unlocked.tsx  「解鎖區」畫面
```

## 8. 測試策略

延續骨架的 Jest 配置：
- `async-storage`、`expo-image-picker` 使用 REUSABLE_INFRA 既有 mock 模板
- `expo-notifications`、`expo-audio` 需新增對應 mock（同樣採「同步回傳 resolved Promise 的 `jest.fn()`」原則）
- `services/` 純函式層（解鎖判斷邏輯、忍術點數/段位計算）需要完整單元測試覆蓋，這是全 App 邏輯正確性最關鍵、也最容易出錯的部分
- 視覺回歸測試沿用 `e2e/visual.sh` 骨架，斷言內容改為 SPARKLIST 三分頁的標題/文字

## 9. 排除範圍（此版本不做）

- 不做多使用者/雲端同步/登入機制，純本機單機 App
- 不做商品分類標籤（使用者已決定不需要）
- 不做「還心動嗎？」獨立確認步驟（已用「未刪除即代表心動」取代）
- 不對六項條件做語意層級的正確性驗證，純粹交由使用者自行勾選判斷
